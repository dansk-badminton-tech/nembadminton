# CI mode

The `Document feature` GitHub Actions workflow runs this skill on a pull request. Its prompt gives you the PR number, the documentation label, and, for a follow-up, the text of a `/docs` comment. The PR head branch is checked out. No one answers questions during the run. These rules replace the matching steps in [SKILL.md](./SKILL.md); the other steps apply unchanged.

- **Evidence (step 1):** read the PR, its linked issue, and its comments with `gh`. Compare against the merge base with `origin/<base branch>`.
- **The given label is final (step 2):** produce what step 2 requires for that label, and leave the PR's labels as they are. For `docs:guide`, find the User Guide that covers the workflow and update it; create a guide only when none covers it, and give it the `journey` front matter from [WRITING-GUIDE.md](./WRITING-GUIDE.md) when the workflow belongs to the holdrunde journey.
- **Existing drafts:** the branch may already contain Help documents, from the feature commits or from earlier runs, for example under the other documentation label. Read them and the commits that added them (`git log <merge base>..HEAD -- resources/help`). Update them instead of creating duplicates, and add only what the label requires but is missing. The branch holds at most one new Release Announcement. Never delete, rename, or revert a file, apart from moving an announcement as described under **Announcement date**: after a switch from `docs:guide` to `docs:announcement`, leave the guide changes in place. The publish script lists them in its comment so the owner can remove them.
- **Open questions become markers (step 3):** write only what the evidence map backs up. Record each point you cannot verify as a TODO(agent) marker, following "Open questions" in [WRITING-GUIDE.md](./WRITING-GUIDE.md).
- **`/docs` follow-ups:** the owner answers open questions in a `/docs <answers>` comment. Treat the answers as evidence: apply each one to the drafts and remove the marker it resolves. Keep every marker the comment does not answer, unchanged; the publish script lists them again. Do not otherwise rewrite the drafts.
- **`/docs refresh`:** the feature may have changed since the drafts were written. Find the first docs agent commit (`git log --reverse --format='%h %s' <merge base>..HEAD`; its subject ends in `(agent)`), and read the code changes after it (`git diff <that commit>..HEAD -- . ':!resources/help'`). Rebuild the evidence map against the current branch and update the drafts to match. Changes to `resources/help` in commits whose subject does not end in `(agent)` are the owner's manual edits: keep them, and change one only where the current code contradicts it. Apply any text after `/docs refresh` as for `/docs <answers>`.
- **Announcement date:** for a new Release Announcement, use the date of the run (`date -u +%F`) for `published` and the filename. Keep the date of an existing draft unless a `/docs` comment asks to change it; then move the drafted file to the new date with `git mv`.
- **Validation (step 4):** run `yarn docs:validate`, then `yarn build`. `unresolved TODO(agent) marker` errors are expected; fix malformed or empty markers like any other error, and every other error the drafts cause.
- **Publish instead of leaving changes uncommitted (step 5):** change only files under `resources/help/guides/` and `resources/help/news/`. When the drafts are done, or when the branch already has everything the label requires, run `node scripts/docs-agent/publish-drafts.mjs` exactly once. Do not commit, push, or comment yourself. The script reruns validation and the build and checks the drafts against the label. If they pass, it commits any changes in one commit (`docs: draft user guide (agent)`, `docs: draft release announcement (agent)`, `docs: apply /docs comment (agent)`, or `docs: refresh drafts (agent)`), pushes it to the PR head branch, and comments with the changed files, the open questions, and any files that no longer fit the label. Otherwise it pushes nothing and comments with the errors.
- **Report (step 6):** report the script's comment as your final answer, since the run log is the only other place it appears.
